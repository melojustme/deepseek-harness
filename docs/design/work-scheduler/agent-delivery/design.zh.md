## 现有实现与扩展位置

提交 `b14d2218f9` 的 Client 通过 `sidebar.footer.action` 和 `shell.overlay` 提供调度面板；Host store 保存版本 2 整份文档；SOP 工具通过同一个 store 更新阶段。当前“开始”和“完成”只改调度状态，新建 Session 只预填草稿。移植必须把这些手动规划状态与真实执行结果分开。

| 所有者 | 设计职责 |
|---|---|
| `client/ui-work-scheduler` | 看板与线程切换、创建、筛选、详情、执行与审查命令；通过声明的 slot 和注入回调使用能力 |
| `client/runtime` 的对象层 | 调度文档修订、执行快照与通知顺序；向组件提供框架绑定的可观察数据 |
| `work-scheduler/work-scheduler-store` | 任务、顺序、执行索引、审查记录的版本化持久化及原子条件更新 |
| 拟新增 `work-scheduler/work-scheduler-execution` | Service Definition：提交、取消、查询、审查与事件协议，定义品牌化任务和轮次 ID |
| 拟新增 `work-scheduler/work-scheduler-execution-local` | Service Provider：原生 Session 执行、worktree、限流、证据固定、恢复与资源释放 |
| `host/apiproxy` 与 `api/remotes` | Consumer：验证请求、Workspace 归属和修订，转发服务方法并投送快照 |
| `work-scheduler/tool-work-scheduler` | 通过条件更新修改其 Session 拥有的 SOP 阶段，不能写运行与审查字段 |
| `bundle/work-scheduler` | 在现有依赖就绪后装配定义、提供者、持久化、传输和 Client 贡献 |

新能力按 Service Definition／Service Provider／Consumer 三个角色一起落地。浏览器组件不接触 Context、不订阅外部状态、不创建 Session 执行器；插件 store 仅保存筛选、选中项、草稿和显示模式。执行独立于面板挂载，关闭面板不会取消任务。该设计不修改 agent loop（智能体循环）。

## 数据与权威来源

| 记录 | 必需内容 | 权威来源 |
|---|---|---|
| Task | 品牌化 `taskId`、Workspace、描述、验收条件、线程位置、人工阻塞信息、当前轮次引用 | 调度存储 |
| Attempt | 品牌化 `attemptId`、提交幂等键、Task 修订、专属 Session、工作目录、基线提交、起止时间、状态、上一轮引用 | 执行服务与持久记录 |
| Evidence | 轮次、Session 日志终止位置、实际检查结果、文件清单、差异摘要哈希、内容定位和完整性标记 | 提供者从原生日志与隔离 worktree 固定的证据 |
| Review | 轮次、证据版本、通过或返工决定、操作者、时间、接受失败检查的原因或返工意见 | 人工命令的持久结果 |
| Snapshot | 文档修订、执行状态、队列原因、已知证据引用及当前连接状态 | Host 快照；Client 按修订消费 |

规划状态不进入模型历史。每次执行的任务文本、验收条件和返工意见通过原生输入接口写入 Session 日志；工具活动、Todo、错误和执行输出继续从原生日志或投影读取。视图不把完整日志复制进调度文档。

调度文档升至版本 3，存储领域版本同步提升；旧格式显式拒绝，并给出执行前导出旧看板的操作说明。若调整 SQLite 布局，单调递增 `SCHEMA_VERSION`；不修改 Session 格式版本。版本 3 不再允许浏览器无条件覆盖整份文档：变更携带 `expectedRevision`，执行和审查字段只由服务命令更新。

## 命令与提交点

下列名称为拟议业务操作，不是现有 API 的声明。最终方法进入类型、验证 schema、传输载体和生成契约同一组改动；RPC 标识符仍由载体层生成。

| 操作 | 输入 | 成功提交点与失败行为 |
|---|---|---|
| 加载／订阅 | Workspace、已知修订 | 返回完整快照；重连以最新修订替换，拒绝倒序通知 |
| 编辑任务／排序 | Task、预期修订、变更 | 条件更新成功后发布；冲突保留草稿并要求刷新 |
| 提交执行 | Task、预期修订、幂等键 | 持久创建唯一排队轮次后返回；重复键返回原结果 |
| 取消 | Task、轮次、幂等键 | 排队取消立即终结；运行取消等待 agent（智能体）及子进程静止后终结 |
| 读取审查 | Task、轮次 | 返回固定证据与完整性；缺少证据或未正常终结不能通过 |
| 通过 | Task、轮次、证据哈希、预期修订、必要接受原因 | 重新核对文件和日志版本，再持久记录通过；变化或冲突拒绝旧审查 |
| 返工 | Task、轮次、证据哈希、非空意见、幂等键 | 原子保留决定并排队新轮次；不重复提交输入 |

服务验证所有 Task、Session、worktree 都属于请求 Workspace。禁止使用用户输入的任意路径作为执行目录。保存、执行、SOP 更新和审查共享按 Workspace 串行的条件变更入口，避免读取旧文档后覆盖其他写入。

## 执行生命周期

接受提交后，服务先创建持久排队记录。线程和额度允许时，为该轮次分配 worktree 和专属 Session，记录准备状态，再通过原生 Session 输入提交任务。收到本轮输入的持久接收凭据后才公布执行中。准备或输入被拒绝时记录失败，不以乐观 UI 代表已开始。

提交使用调用方生成的稳定幂等键，轮次与输入接收凭据建立持久关联。崩溃可能发生在发送与写回之间，因此恢复先查询该 Session 的已记录输入；不能确定是否接收时显示中断并要求人工核对，绝不盲目重发。Session 的一般 idle 通知不能替代本轮的接收凭据、完整执行区间和终结证据。

每个线程一次只占用一个任务。待审查继续阻塞线程；通过或显式异步让出后，后续已提交任务才可进入准备。跨线程只使用配置允许的额度，不自动提交尚未排队的待办。`maxConcurrentRuns`、等待队列容量、证据显示上限和保留策略是经过验证的 Config 字段。

取消控制器同时拥有准备、运行和释放过程。重复取消幂等；准备中的取消回滚已分配资源；运行取消先请求原生终止，再等待执行及子进程退出。完成、取消和错误竞争时只允许一个终态提交；所有事件按轮次归属检查，旧轮次不能更新新轮次。

Host 重启遍历未终结记录，与 Session 日志和实际执行资源核对。已完成且证据完整的轮次可恢复审查；仍有可验证执行所有者的轮次恢复监控；其余标为中断。插件 dispose（资源释放）先停止接收命令和发布通知，再取消并等待所拥有的运行资源；worktree 产物按保留策略保留，禁止清理用户原始目录。

## 差异与审查

首轮以用户选择的 Git 提交为基线，默认当前 HEAD；原工作区未提交改动不自动进入执行，并在提交前显示提示。返工使用上一轮保留的产物快照作为输入，创建新的隔离执行目录。提供者可以创建仅本地的内部快照提交以固定基线，但不移动用户分支、不推送。执行前须显示这个行为；若需要复制原工作区未提交内容，属于后续独立设计。

正常结束后，提供者固定文件清单和内容哈希，覆盖 tracked 与 untracked 文件；差异结果绑定基线、轮次、日志终止位置和内容哈希。二进制文件展示元数据，超限文件展示截断及完整产物入口，不伪装成没有修改。原型的逐行差异是样例数据，正式实现复用原生 diff 展示能力和文件访问策略。

检查证据来自实际工具调用及结果，明确命令、工作目录、退出码和是否被中断。不能可靠识别为检查的命令保留在工具记录中，不自动标为测试通过。通过操作允许用户有理由地接受失败检查，但不允许接受未终结执行、不完整证据或已经变化的差异。通过只产生审查记录；产物继续留在该 worktree，合入分支由后续显式工作完成。

## 交互与可访问性

窗口继续使用已有缩放与全屏行为。主区域提供状态看板和线程视图，顶部显示 Workspace、连接状态、运行额度、搜索和创建入口。选中任务时，详情区呈现描述、验收条件、轮次和概览／日志／差异三个页签。

执行中显示原生 Todo 计数和当前工具活动；等待用户时提供跳到原生审批或问题的操作。待审查提供通过、返工意见和完整 Session 入口。无任务、无工作区、加载、错误、断线、版本冲突都有文字状态；断线期间禁用变更操作。小屏看板折为单列，详情使用全屏抽屉并保留返回按钮。

卡片和动作可通过键盘访问。拖动排序提供“上移／下移”替代；进度使用实际计数的 `progressbar`；动态通知使用温和的 `aria-live`。关闭详情恢复卡片焦点；`Escape` 从最内层编辑器开始关闭，不触发取消执行。状态同时使用文字和颜色。
